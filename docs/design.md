# 設計の理由

操作方法は [README](../README.md)、書式は [Resource 仕様](resource.md)、配布の手順は [公開手順](publishing.md) を参照。

## 作者用定義と配布用定義

**作者用定義**は作者が編集する課題定義。`latest` などのタグで、公開時点のイメージを使う意図を表せる。**配布用定義**は公開時にイメージを digest で固定した定義。同じ課題バージョンの実行イメージは公開後に変更しない。

タグを作者用定義で許可すると、イメージ更新のたびに digest を手で転記せずに済む。一方、配布後もタグを解決し続けると実行内容が変わるため、公開時にだけ固定する。通常の reader と validator には固定を要求するモードを設けない。

イメージの再利用はビルドキャッシュに任せる。入力ハッシュと digest の対応表を独自に管理しないことで、管理対象を減らす。代わりに、同じ入力でも再ビルドで digest が変わり得ることと、キャッシュ未命中時のビルド時間を許容する。

## 課題ごとに Immutable Release を使う

課題 ID とバージョンごとに GitHub Release を作成すると、他の課題の更新と独立して公開・取得できる。公開済みバージョンは Release 一覧で管理し、`resources.yaml` に履歴を重複して持たせない。

release immutability は公開後のアセット差し替えと関連タグの変更を防ぐために使う。Release 自体の削除を防ぐ保証ではない。配布物を別ブランチで管理する方式は採用しない。

## ライブラリの責務をローカルな入出力に限定する

取得・認証・展開・採点・更新管理は呼び出し側が担う。ライブラリは `fs.FS` を受け取り、課題内の通常ファイルをメモリに取り込んでから、検証済みの定義と参照素材を返す。入力 filesystem を保持しないため、呼び出し後の読み込みや入力の寿命管理が不要になる。

YAML の構造は JSON Schema、ファイルと参照関係は Go で検証する。CLI も同じ処理を使い、イメージのビルドや Release の公開は公開スクリプトが担う。

## 課題の取り込みと検証を分ける

公開関数 `Read` と `ReadManifest` は `fs.FS` を受け取り、共通の取り込み処理を行う wrapper とする。ローカルディレクトリと ZIP の違いは呼び出し側が標準ライブラリで扱う。取り込み時は全階層の symlink、`.` で始まる名前、`node_modules` ディレクトリを除外する。symlink は辿らず、除外ディレクトリ内は走査しない。必要な定義・素材が除外された場合はファイル不存在として検証に失敗する。

除外後の通常ファイルは未参照のものも一括で afero の `MemMapFs` に読み込み、空ディレクトリも保持する。内部の `read` と `readManifest` はメモリ上だけで検証する。課題ディレクトリは `BasePathFs` で切り出すため、各課題の検証時に入力 filesystem を再走査したり、サブツリーを複製したりする必要はない。定義や素材としてディレクトリを指定した場合はエラーにする。

`ReadManifest` は入力全体を取り込むため、登録課題以外の通常ファイルにも読み込みコストがかかる。その代わり、取り込みと検証で除外ルールを共有でき、課題ディレクトリまでの symlink 検査も不要になる。返す素材は定義が参照するものだけとする。

入力は呼び出し中に変更しないことを前提とする。hardlink は通常ファイルとして読み、inode の共有を検査しない。メモリへの取り込みは、同時書き換えの検出や、ある一時点の内容の取得を保証するものではない。
